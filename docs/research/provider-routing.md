# Provider discovery and routing research

Research for [Provider discovery and routing, issue 7](https://github.com/dvcol/devkit-extension/issues/7), checked on 2026-09-23. This note identifies reusable APIs and remaining decisions, including an executed two-hub connection-isolation experiment. It does not adopt a routing policy or implement discovery. The full server-plus-extension routing experiment remains unrun.

## Already settled

- Provider identity, realm, execution and target are separate. Slots use provider ID, capability ID and exact positive-integer contract version. Package versions do not select capability contracts.
- Select before dispatch. A resolved binding remains pinned to its provider, and an action's required capabilities bind there by default. Cross-provider orchestration is explicit.
- After dispatch, never reroute or automatically replay a call, including reads. A timeout, disconnect or claim that execution did not start does not relax this rule. A separately requested call makes a new routing decision.
- Targets carry `kind`, opaque `id` and `generation`; adapters validate them. Native contexts remain local. Remote clients receive serializable metadata, without native browser handles or transports.
- Broadcast, callbacks, provider-ID/realm preferences, and UI choice passed into a callback are required modes. Contributions supply defaults and calls can override them. The precise precedence/composition rules are still proposals in issue 7.
- Providers keep separate state; synchronization belongs to issue 8. Domain classification belongs to embedding applications. Packaged build-time composition and optional CDB integration are already selected.

These are constraints for the next discussion, not questions to reopen. [Architecture](../../ARCHITECTURE.md), [issue 7](https://github.com/dvcol/devkit-extension/issues/7).

### Executed connection-isolation failure

The [retained probe and results](../probes/provider-connection-isolation/README.md) exercise two real authenticated hubs on separate bases of one Vite preview server. The clients use the released Devframe API and kit's published client wrapper. One Node process owns both hubs; this is not a genuine KitNodeContext/DevTools host, an extension host, or the full routing experiment below. The actual browser reports Chrome 152.0.0.0 in the in-app user agent, not a verified current-stable browser matrix.

| Scenario                                                                     | Actual observation                                                                                     | Adapter implication                                                                          |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Connect to A, then request B using only another `baseURL`                    | The second client inherits A's connection metadata and increments A.                                   | A URL alone does not establish independent dialing.                                          |
| Explicit A connection and B connection metadata, with distinct static tokens | Separate endpoint receipts, counter values and state subscriptions.                                    | Explicit descriptors solve initial endpoint selection in this topology.                      |
| A exchanges a freshly requested authorization code                           | B's public connection descriptor changes to A's issued token.                                          | Initial explicit credentials do not isolate later authentication updates.                    |
| Recreate B from that descriptor                                              | B becomes unauthorized; its protected action rejects and its handler count remains 2 before and after. | Continued success on B's already trusted connection concealed a broken reconnect credential. |
| Recreate B with its original explicit token, then close A                    | B works again and remains connected, incrementing to 15 after A closes.                                | Owned client close is isolated in the tested case; credentials require a separate fix.       |

The probe's `passed: true` records successful reproduction of this defect and its controls, not successful authentication isolation. Browser observations and Node handler receipts agree. Both hubs and preview close successfully; the owning process exits 0, and a subsequent request to the preview endpoint is refused. The final retained source passes strict TypeScript 7, type-aware Oxlint with warnings denied, and Oxfmt. An earlier fixture error that required optional metadata is preserved separately with its correction.

Released Devframe 1.0.0 `dist/client/index.mjs` resolves explicit `connection`, then `connectionMeta`, then the stored connection, before fetching `baseURL` (lines 483–529). Setup writes shared globals and local storage. The full client creates a same-origin `devframe-auth` BroadcastChannel; successful code exchange broadcasts a token, and other clients pass it into `requestTrustWithToken` without a provider discriminator (lines 1866–1869, 1912–1934 and 1996–1998). An already trusted server session accepts the subsequent handshake before checking the changed token, explaining why the failure appears when B is recreated.

The released public options provide no switch or namespace for these shared effects. `simpleAuth: false` and `otpParam: false` disable automatic prompts/code handling, not the channel. Explicit connection metadata is therefore insufficient for the server adapter's full authentication isolation requirement. Do not mutate private browser globals, import `devframe/internal`, or replace the RPC/state engine to conceal this gap. Same-origin parent inheritance, separate Node processes/origins, revocation, and process-restart recovery remain untested.

### Tested upstream isolation proposal

The separate [issue 6 prototype](../probes/provider-connection-isolation/proposal/README.md) adds an experimental `isolateConnection: true` option to a disposable copy of Devframe 1.0.0. It skips shared discovery/token caches and the authentication BroadcastChannel while preserving the full RPC/state client. The option is neither a released upstream API nor an adopted SDK declaration. No workspace dependency or upstream checkout was patched.

Three real-browser profiles used the same proposed package: default clients reproduced both defects; two isolated clients selected separate endpoints and retained separate credentials; an isolated B alongside a default A also retained B's credential after A exchanged its code. In both isolated profiles, B was then closed and recreated from its public descriptor, authenticated successfully and reached its own receipt handler exactly once. After A closed, B remained connected and incremented to 17. All three profiles recorded successful hub/preview cleanup and exited 0; subsequent HTTP requests were refused.

The browser checks include a bounded 250 ms observation of B's unchanged token, followed by the actual authenticated recreation and handler receipt. They are not an unlimited-duration broadcast guarantee. Eight direct boundary tests separately cover cache reads/writes, explicit connection/metadata/base discovery, local token updates, omitted/false default behavior and auth channel creation/cleanup. Strict TypeScript 7, type-aware Oxlint and Oxfmt pass for the prototype verification sources. Exact patches, hashes, executed source and separate browser results are retained. These findings support a narrowly scoped upstream proposal; package distribution, adoption and the full supported-host matrix remain unresolved.

## Two real-provider experiment proposal

This complete server-plus-extension experiment is proposed work after the numbered decisions below. It has not run; the bounded two-hub subcase above supplies only connection/authentication evidence.

1. Run one genuine Devframe/hub server provider and one packaged extension background provider against an owned loopback page. Repeat the server side through genuine Vite DevTools/kit and the browser side on the selected current stable Chromium and Firefox baselines, recording actual versions. Reuse native RPC and runtime ports; no mock provider or renamed local controller counts as a host.
2. Expose the same versioned counter operation through both providers, with separate counters and server/background execution receipts. Include one target-required operation whose receipt names the inspected document generation. The adapter must establish the target association; matching URLs alone cannot prove that two providers refer to the same document.
3. Exercise defaults, exact-ID override, realm preference, callback input and broadcast with one selector function shared by a non-UI test consumer and the eventual JSON selector UI. The UI assertion waits for issue 12's real renderer contract; do not invent a view schema for this probe. Capture sanitized candidate snapshots, selected identities, dispatch receipts and independent counter values.
4. Pause between selection and dispatch, disconnect the chosen connection, and verify the chosen pre-dispatch policy. Separately let a mutation execute, drop its response, and prove the other counter stays unchanged. Navigate the target during selection and during an in-flight call; stale generations must not acquire successor ownership.
5. Restart only one provider, then remount only the client UI. Assert the selected logical-ID/incarnation policy, catalog resynchronization, old binding fencing and listener removal. A disconnected catalog remains distinguishable from an authoritative empty one. Never infer cleanup from elapsed time.
6. For each broadcast outcome, retain successes alongside permission and transport failures. Two providers can cover these over successive scenarios; add a third real provider if the acceptance test requires all three outcomes in one broadcast. A missing permission fixture must not be described as a real user denial.

Extend the executed same-document isolation subcase to a genuine Vite DevTools server and the selected upstream isolation fix before advertising support for multiple server instances. Retain explicit descriptors, distinct credentials, token exchange and close/recreate checks. Add the optional CDB profile using its real connection/bootstrap and shared target owner; do not require a daemon for the extension-only profile. CDB's broker path is an optional composition, not the mandatory discovery mechanism for every provider.

Issue 14 owns the complete API-to-example-to-test inventory. This probe establishes routing evidence; it does not replace renderer, permission, state-recovery, debugger or reload conformance.

## Remaining decisions and their dependencies

The owner accepted stable configured identity and client-composition ownership after clarifying Vite's lifecycle. The [current contract record](../planning/007-provider-routing.md) separates those settled boundaries from the remaining questions.

1. **Logical identity and incarnation, settled boundary.** The host configures a stable provider ID; the adapter creates a fresh incarnation for each backend lifetime. UI HMR and reconnecting to the same live backend do not recreate it. Cross-profile/project identity collisions and authoritative registry update rules still need explicit handling.
2. **Discovery ownership, settled boundary.** The client application's composition root owns the registry and composes explicit endpoint, verified host-page handoff and extension-local adapters where supported. Consumers receive metadata through their actual local/remote integration. No global daemon, automatic port/origin scans or persistence of discovered hosts is implied.
3. **Candidate and catalog readiness.** Define the immutable, serializable candidate view, authoritative snapshot/revision boundary and distinctions among unknown discovery, empty catalog, missing permission, unsupported operation and disconnected provider. Core already supplies availability reasons; it does not define a registry subscription or first-sync protocol. Trust and per-principal filtering remain issue 9's responsibility.
4. **Directive/default composition and ambiguity.** Per-call replacement of lower defaults and no inherited fallback for exact pins were already accepted in core Q6. On 2026-09-24 the owner confirmed ambiguity errors requiring an explicit UI/agent/caller discriminant. Remaining work is compact selector syntax and callback zero/multiple/stale selection behavior. The owner proposed a contribution-local `routing` property accepting realm/provider choices, ordered alternatives or a callback; realm/provider namespaces must be unambiguous.
5. **Pre-dispatch races and waiting.** The owner confirmed ordinary calls use readiness at dispatch and do not queue for connecting providers. Only explicit policy alternatives may be considered before dispatch. A provider dropping during execution fails the invocation; the client may explicitly request another call. Define the exact handoff where queued upstream work becomes dispatched, and callback cancellation/deadline behavior. Post-dispatch fallback/replay remains prohibited for all calls.
6. **Broadcast return shape and cancellation.** Separate capability/action broadcast methods are accepted. Ordinary invocation retains `Promise<Value>`, with a single request object or at most two/three clear arguments in the final API. Define snapshot ordering, duplicate selection handling, zero candidates and canceled/unanswered outcomes. Successful siblings must survive a rejection; cancellation cannot certify that native work was undone.
7. **Where routing defaults live.** Current service/action/plugin definitions have no routing-default field, and `RoutingDirective` is deliberately opaque. The owner's inline-contribution counterproposal remains under review; the earlier separate-client-policy proposal is not accepted. Establish how defaults become available before provider selection without importing or transporting backend handlers/callback code. A bound capability API remains provider-pinned regardless of that choice.
8. **Adapter identity mapping and trust handoff.** Define the server/extension/CDB identity mapping, who issues document generations, and how the same physical target is related across providers. Preserve native access and one debugger target owner. CDB already has broker-scoped provider/instance IDs and target generations, but those names alone do not settle the generic mapping. Coordinate with issues 8–11 rather than adopting their policies here.

The next owner discussion addresses compact contribution-local declarations and how clients obtain their routing defaults. Callback snapshots and broadcast edge cases follow that shape. Accepted behavior can be recorded while declaration details remain open. Nothing in this note closes issue 7 or establishes complete host conformance.
