# Browser capability research

Research date: 2026-09-22. Issue: [Browser capability audit #3](https://github.com/dvcol/devkit-extension/issues/3). Owner: `dvcol`. Research branch: `dvcol/research/browser-capabilities`, based on `1edb3d87af2cc8f3ca15a2cc0019b37ccf6b2ba0`.

Status: closed with [published resolution](https://github.com/dvcol/devkit-extension/issues/3#issuecomment-5778483567). Current-stable native-browser experiments passed on Chrome for Testing `153.0.8010.52` and Firefox `156.0.1`. Chromium native DevTools coexistence passed both attachment orders, with and without active response interception, with both clients independently evaluated after attachment. Firefox response filtering, absent-filter-permission rejection, MAIN timing and isolated-world separation passed. This resolves bounded platform feasibility. The report assigns remaining recovery, permission-transition, renderer and integration guarantees to named contract owners; no SDK has been implemented.

## Scope and evidence labels

The target is a generic SDK with build-time contributions and browser-specific implementations. The initial browser inventory is desktop Chromium and Firefox. Chromium derivatives, mobile browsers and Safari need separate evidence before admission. None was tested here.

The matrix distinguishes four kinds of evidence:

- **Observed** means the exact operation passed in the isolated experiment below, on the recorded browser build. The broader SDK guarantee remains unresolved.
- **Documented** means a first-party reference describes the operation. Actual integration remains unresolved.
- **Unsupported** means the documented browser API or delivery mechanism does not provide the requested operation.
- **Unresolved** marks conflicting documentation, missing experiments or a product decision. It must not become a silent successful fallback.

All linked web documentation and compatibility data were inspected on the research date. API introduction versions below are compatibility facts, not shipping floors. The user selected **current stable Chromium and Firefox** as the initial support baseline, advancing with stable releases. This audit adds no ESR, historic-version, derivative-browser, mobile or Safari guarantee. A release must record exact tested versions and rerun the affected capability checks before advancing its support record.

Official channel metadata, retrieved on 2026-09-22, identified CfT `153.0.8010.52`, revision `1681091`, and Firefox `156.0.1`. The downloaded binaries reported those versions. They ran in fresh owned profiles on macOS `26.6.2`, build `25G83`, with Node `26.9.0`. The metadata is retained in [stable-channel-metadata.json](./browser-capabilities-evidence/stable-channel-metadata.json). Installed or cached browser versions did not select the baseline. This macOS execution record does not establish Windows or Linux parity. [Google CfT channel metadata](https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions-with-downloads.json), [Mozilla release metadata](https://product-details.mozilla.org/1.0/firefox_versions.json).

In the matrix, “supported native” means the bounded native operation was observed on these stable builds. “Documented; unresolved” means the API exists but the promised integration remains an acceptance gate. SDK ownership, recovery and public error schemas remain subsequent contract and implementation work.

## Constraints that affect the contract

### Native context is local and narrower than realm

The experiment observed `chrome.runtime.sendMessage` in the isolated content world and its absence in MAIN. It also observed that content code cannot use `chrome.debugger`. A `realm: 'webext'` check alone therefore cannot establish access. The contract needs execution-context narrowing and available permissions. Privileged registration belongs in an eligible extension context. Remote consumers receive descriptors, IDs and serializable results.

MAIN scripts share their environment with page code. Mozilla explicitly warns that page code can observe or interfere with them. Do not treat a page-origin message or a page-supplied contribution ID as authority to invoke a privileged action. The page channel needs validation and an independently authorized operation registry. [Mozilla execution worlds](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/ExecutionWorld).

Chrome describes `document_start` as running before page DOM construction and other scripts, but that does not turn late registration into a pre-navigation guarantee. MAIN follows the page CSP; isolated and unpacked contexts have different policies. The plain HTTP fixture tested neither strict CSP nor deployed-site restrictions. [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts).

### Scope of debugging and interception

The documented Chromium domain set is `Accessibility`, `Audits`, `CacheStorage`, `Console`, `CSS`, `Database`, `Debugger`, `DOM`, `DOMDebugger`, `DOMSnapshot`, `Emulation`, `Fetch`, `IO`, `Input`, `Inspector`, `Log`, `Network`, `Overlay`, `Page`, `Performance`, `Profiler`, `Runtime`, `Storage`, `Target`, `Tracing`, `WebAudio` and `WebAuthn`. This is not unrestricted browser-level CDP. Policy can also prevent attachment. [Chrome debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger).

The Fetch schema requires a paused response for `getResponseBody`; redirects do not expose a body through that command. Taking a response stream has different continuation rules. The successful buffered ASCII fixture does not establish a streaming transform API. [Fetch protocol schema](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Fetch.pdl).

Firefox filtering owns the stream until it closes or disconnects. Script byte caching requires early filter creation. Service-worker script interception additionally needs `webRequestFilterResponse.serviceWorkerScript` from Firefox 95. Tests must cover chunk boundaries and cleanup, not just replace text in the first chunk. [Mozilla filterResponseData](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webRequest/filterResponseData).

### Background recovery and permissions

Chrome normally terminates idle workers after 30 seconds; an event or extension API call resets that timer. Long operations have other limits. Debugger sessions and some active communication extend worker lifetime, so leaving inspection attached invalidates an idle-lifecycle experiment. Firefox's event page can also unload. Neither process should be the only owner of durable state. [Chrome lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [Mozilla background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background).

`activeTab` is a temporary grant triggered by user invocation, not persistent authority for every domain. Hosts may be denied or revoked. Runtime permission requests require an eligible user gesture; a background reconnection is not such a gesture. Test missing grants independently from unsupported implementation and restricted target errors. [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [Chrome permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions), [Mozilla host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions).

### What HMR can mean

Keep four testable modes separate: server-hosted development HMR, a live backend serving watched production output, unpacked-extension code reload/reinjection, and installed production extension updates. The shared JSON interface may receive data updates in each applicable mode. That alone proves neither module replacement nor preserved listeners, state, target ownership or renderer identity.

Chrome's policy permits fetched configuration when the package contains its logic. It also forbids evading the remote-code restriction through an interpreter for complex commands fetched as data. Its debugger and userScripts exceptions apply to their documented purpose, not the entire extension. A JSON renderer must not silently become a privileged remote-code loader. Firefox separately prohibits weakening page security headers. These are delivery constraints to check against the eventual module design, not a finding that any particular implementation is store-approved. [Chrome MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements), [Mozilla policy](https://extensionworkshop.com/documentation/publish/add-on-policies/).

## Current-stable coexistence and Firefox experiments

The retained [Chromium runner](./browser-capabilities-evidence/chromium-coexistence.mjs) launches a fresh headed CfT process for each case. Node uses browser-level CDP to discover targets and open the real Network frontend with `Target.openDevTools`; `Target.getDevToolsTarget` confirms its identity. It attaches only to its own extension control document and briefly to the frontend document. It never calls `Target.setAutoAttach` or attaches a controller session to the inspected fixture. Extension commands travel through `chrome.runtime.sendMessage` to the extension worker. [CDP Target schema](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Target.pdl), [Chromium protocol browser tests](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/devtools/protocol/devtools_protocol_browsertest.cc).

Frontend readiness requires `document.readyState === 'complete'` and its own SDK TargetManager containing the fixture URL. After both clients attach, the probe invokes `Runtime.evaluate` through the frontend's **existing** RuntimeAgent and asserts `54`, then invokes the extension's debugger connection and asserts `42`. No third connection to the inspected target is introduced. This frontend inspection uses its internal `core/sdk/sdk.js` module; it is a version-specific research mechanism, not a public SDK dependency.

The [final event/results JSON](./browser-capabilities-evidence/chromium-coexistence.json) preserves target IDs, readiness snapshots, both evaluations, paused-response events, request results, and explicit disable/detach cleanup. It resolves the previously contradictory documentation only for these tested conditions. It does not guarantee every native panel interaction, debugger breakpoints, child targets, multiple extensions, target replacement, cancellation or future releases.

The [Firefox runner](./browser-capabilities-evidence/firefox-filtering.mjs) uses `web-ext` `10.7.0`, Firefox `156.0.1`, a temporary headless profile and packaged MV3 `background.scripts`. It never supplies the user's profile. With `webRequest`, `webRequestBlocking`, `webRequestFilterResponse` and loopback host permission, page-observed text becomes `changed-text`, HTML body becomes `changed-html`, and an injected HTML-byte marker exists before the original parser script. A UTF-8 response split across three network writes, including one split inside a multibyte character, becomes `changed-café-世界`; the filter records three chunks. The implementation buffers until `onstop`, then writes once and closes. **Incremental downstream streaming was not tested.** [Mozilla filter API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webRequest/filterResponseData), [web-ext reference](https://extensionworkshop.com/documentation/develop/web-ext-command-reference/).

Both Firefox cases assert that MAIN ran before the first parser script, that MAIN cannot see isolated globals or runtime messaging, and that isolated code can message the background without seeing MAIN's marker. The background reports `typeof browser.debugger === 'undefined'`. The second manifest omits only `webRequestFilterResponse`; all three calls reject with `Missing required "webRequestFilterResponse" permission` and the page receives unchanged bodies. This is **absent permission**, not a user denial or revocation. The final probe waits for page, isolated and all three terminal filter reports before asserting. [Firefox results](./browser-capabilities-evidence/firefox-filtering.json).

### Setup failures retained

Earlier Chromium localhost-polling control stalled, and the browser-session Extensions storage API rejected `No associated browser context`. They are controller failures, not feature unavailability. An explicit extension control-page session removed that context mismatch. Headed and headless fixture navigation still stalled with zero server requests until the final isolated process used `--password-store=basic` and `--use-mock-keychain`, the macOS test flags also used by Playwright. The comparison establishes that these flags removed this fixture's stall; it does not prove the underlying OS prompt or keychain cause. No native computer permissions or UI automation were used. [Playwright launch flags source](https://github.com/microsoft/playwright/blob/v1.63.0/packages/playwright-core/src/server/chromium/chromiumSwitches.ts).

The first Firefox fixture used request match patterns containing the ephemeral port and did not wait for a permission-readiness report. It saw no filter events. Changing the filter to the documented host match form `http://127.0.0.1/*`, narrowing paths inside the callback, and completing the permissions report before navigation yielded the passing cases. Because both setup details changed, this is not a separately isolated cause analysis. Retained failure files and their scope are listed in the [evidence README](./browser-capabilities-evidence/README.md).

## Context, permissions and activation requirements

| Context                                            | Activation and authority                                                                                                                      | Lifetime and restrictions                                                                                           |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| MAIN page script                                   | Predeclared packaged content script or an eligible `scripting` caller with host grant/`activeTab`.                                            | Page realm and page CSP; no privileged extension namespace. Navigation replaces the document.                       |
| Isolated content script                            | Matching declared script, or authorized one-shot/dynamic injection.                                                                           | Limited extension API subset; no raw debugger. | Chromium service worker / Firefox event background | Registered browser entry point; module-specific permissions remain required.                                                                  | No durable global-state guarantee; use top-level event registration and persist required state.                     |
| Popup and options                                  | Declared `action.default_popup` or options entry point; creation itself has no extra host permission.                                         | Packaged extension document. Each operation still needs its own permission; popup closes/disposes independently.    |
| DevTools page/panel/sidebar                        | `devtools_page` registers while native DevTools opens; `chrome.devtools` belongs to that context.                                             | Lifetime follows DevTools. Inspected-page authority does not become background `chrome.debugger` access.            |
| Browser side panel/sidebar                         | Chromium `sidePanel` permission and eligible user interaction for `open`; Firefox `sidebar_action`/`sidebarAction`.                           | Browser-specific presentation and interaction rules. No observed native UI lifecycle claim here.                    |
| Network filter or debugger backend                 | Firefox explicit filtering permissions plus hosts; Chromium mandatory manifest `debugger` for this route, or DNR permissions/hosts for rules. | Paused-request and filter-stream ownership requires finite cleanup. Debugger is not an optional runtime permission. |

These details follow the context-specific primary sources in the capability matrix and [Chrome optional permission exclusions](https://developer.chrome.com/docs/extensions/reference/api/permissions). Property existence alone is not authority, readiness or correct execution context.

## Required coverage mapping

The contract work must maintain an inventory mapping every SDK-owned public API, export, hook and feature to a runnable contribution example, an actual host and an automated assertion. The overall example suite must include contributions, renderers, Devframe, Vite DevTools, Chromium and Firefox. Every declared supported API/host/mode cell needs successful execution; failure and lifecycle cases are additional assertions. Explicitly unsupported cells need an asserted unavailable result, with the remaining host still functional. Missing cells block an implementation-complete claim. Mocks and type checks are supplemental.

For raw native access, test local context narrowing, permission handling, target ownership, cancellation, listener disposal and serialization boundaries owned by the SDK. Do not expand that requirement into retesting every vendor API implementation. Include inspected target generations so that an operation intended for a replaced document cannot silently affect its successor. These are accepted coverage obligations for contract resolution; no SDK API inventory exists yet.

The accepted semantic baseline distinguishes:

| Availability condition     | Meaning and evidence boundary                                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unsupported implementation | The selected browser/backend has no implementation, such as Firefox native debugger or DNR body transform. Another registered capability can still work.                     |
| Wrong execution context    | The feature exists but this local context cannot expose its raw object, such as a content script requesting raw debugger. A permitted remote action is a separate operation. |
| Missing permission         | Required authority is absent. Firefox filter rejection was observed. User refusal and revocation require their own state transitions and were not simulated by this fixture. |
| Restricted target          | The browser forbids access to this target even when the module exists. Chrome internal-page injection rejection was observed.                                                |
| Disconnected backend       | A previously selected provider or transport is gone. Keep this separate from static lack of browser support.                                                                 |
| Conflicting owner          | Another owner prevents the operation or owns the target/request. The simple native-frontend coexistence result does not remove this possible condition.                      |
| Stale target               | The tab/document/frame generation changed or closed before completion; the operation must not silently act on a replacement.                                                 |

[Contribution and realm contract #5](https://github.com/dvcol/devkit-extension/issues/5) must choose public names, serialization and retry rules that preserve these distinctions. Observable availability changes and watch disposal remain SDK tests. Descriptors, IDs and serializable failures may cross RPC; native namespaces, listeners and live handles remain local. No error class or watcher implementation is claimed by this audit.
