# Upstream reuse audit

Research for [Upstream reuse audit](https://github.com/dvcol/devkit-extension/issues/2), checked **2026-09-22**. The audit is closed with its [canonical resolution](https://github.com/dvcol/devkit-extension/issues/2#issuecomment-5778116319), acceptance handoffs on the nine dependent decision tickets, and a named pointer in the parent map. The issue's Definition of Done permits observed feasibility evidence or named follow-up decision tickets. Browser integration and future SDK conformance remain obligations of those tickets, not reverse dependencies on this audit.

The operational baseline is the exact published packages, their verified integrity records and public exports. Source/main comparisons explain implementation boundaries; this report makes no claim of complete source-to-package equivalence. It records source, package and bounded runtime evidence, not a completed SDK or browser conformance result.

The evidence supports **selective reuse through local provider adapters**. JSON-render authoring can remain framework-neutral while the reference renderer uses Vue internally. Several useful browser entry points already exist. A complete Devframe or Vite DevTools Node context cannot serve as the portable extension backend unchanged.

## Evidence and release baseline

Three evidence levels are distinguished throughout:

1. **Source:** inspected checkout files and selected files fetched from pinned upstream main revisions.
2. **Release:** npm registry version metadata plus downloaded, checksum-checked package tarballs and their actual export maps.
3. **Experiment:** isolated browser-target bundling and a small Node runtime exercise using released packages. Neither experiment loads a browser extension.

### Compatibility and ownership

- The Devframe 1.0.0 family uses exact `1.0.0` peer relationships. `@devframes/vite@1.0.0` accepts Vite `^7.0.0 || ^8.0.0`. DevTools kit `0.7.5` depends on Devframe, hub, and JSON-render `^1.0.0`; DevTools `0.7.5` pins kit `0.7.5`. Preserve one coherent family when choosing the implementation baseline. These are declared constraints, not proof of every allowed combination. [Vite metadata](https://registry.npmjs.org/@devframes%2fvite/1.0.0), [kit metadata](https://registry.npmjs.org/@vitejs%2fdevtools-kit/0.7.5), [DevTools metadata](https://registry.npmjs.org/@vitejs%2fdevtools/0.7.5).
- `@dvcol/cdb-devframe@0.3.0` pins Devframe, hub, JSON-render, and renderer **exactly `1.0.0`** and declares Node `>=24.0.0`. Its `0.2.0` release instead pins the Devframe family at `0.9.10`. Mixing the old local CDB baseline with the locally inspected Devframe `0.9.18` is not the declared integration combination. [CDB Devframe 0.3.0](https://registry.npmjs.org/@dvcol%2fcdb-devframe/0.3.0), [0.2.0](https://registry.npmjs.org/@dvcol%2fcdb-devframe/0.2.0).
- `@devframes/json-render@1.0.0` depends on `@json-render/core ^0.20.0`. The renderer's published manifest records `@json-render/vue ^0.20.0` as a build dependency. Upstream core and Vue renderer are now published at `0.21.0`; that newer version is outside `^0.20.0`. Do not upgrade the underlying schema family independently without compatibility evidence. [Wrapper metadata](https://registry.npmjs.org/@devframes%2fjson-render/1.0.0), [renderer metadata](https://registry.npmjs.org/@devframes%2fjson-render-ui/1.0.0), [upstream core](https://registry.npmjs.org/@json-render%2fcore/0.21.0), [upstream Vue](https://registry.npmjs.org/@json-render%2fvue/0.21.0).
- Audited Devframe, Vite DevTools, and CDB manifests declare **MIT**. Upstream `@json-render/core` and `@json-render/vue` declare **Apache-2.0**. Preserve applicable notices when packaging the bundled renderer; this audit did not perform a transitive license compliance review. [Devframe metadata](https://registry.npmjs.org/devframe/1.0.0), [DevTools metadata](https://registry.npmjs.org/@vitejs%2fdevtools/0.7.5), [CDB metadata](https://registry.npmjs.org/@dvcol%2fcdb/0.3.0), [JSON-render core metadata](https://registry.npmjs.org/@json-render%2fcore/0.21.0).

### Main and release parity limits

GitHub comparison showed Devframe main 26 commits ahead and one behind the inspected checkout; DevTools main was 52 ahead and three behind. Selected files were then compared rather than treating ancestry as semantic proof. Devframe's renderer registration helper, browser renderer registry, and Vite hub adapter were byte-identical; JSON view creation changed its Standard Schema type import. DevTools kit context was byte-identical. DevTools server code changed, including build capability-token authentication, so old authentication observations must not be generalized to `0.7.5`. [Devframe comparison](https://github.com/devframes/devframe/compare/a3f967755af99a0a0d8dd82b7b5d4f3dd4aec0bc...18fa60effeb928eb445add2a536cd44906a59981), [DevTools comparison](https://github.com/vitejs/devtools/compare/121656dfc5866b2f8de5baa8e0b6166ec28599c8...ad2d6df720a513670f93ac09318ae6dc8b4a0623), [current DevTools server](https://github.com/vitejs/devtools/blob/ad2d6df720a513670f93ac09318ae6dc8b4a0623/packages/core/src/node/server.ts).

The CDB comparison API could not resolve the local `89bdf…` revision. Its embedded bridge, selected-tab publisher, provider connection contract, and Devframe connection source files were byte-identical to fetched main files. This establishes parity for those four files only. Registry records supplied no `gitHead` for the audited releases. Exported symbols and selected built implementation paths were inspected in tarballs, but there was no reproducible source build or complete source-map comparison proving every package byte came from the stated main revisions. Complete published/main equivalence is unproved and is not assumed by the adoption recommendation. [CDB embedded source](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/core/src/embedded.ts), [connection source](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/devframe/src/connection.ts).

Use exact released artifacts as the operational baseline, recording version, registry integrity and exported entry points. This answers what can actually be consumed without requiring a full reproducible upstream build. The alternative is to build every adopted package from a pinned source revision and establish reproducibility; that would answer a stronger provenance question but is unnecessary for this audit's stated scope. A future source-only change requires its own package/export compatibility check before adoption. [Release and conformance contract #16](https://github.com/dvcol/devkit-extension/issues/16) owns upgrade gates and any stronger provenance policy.

## Behavior traces and design consequences

### JSON UI, action dispatch, and context layering

Existing server flow is: a Node context publishes a `createJsonRenderView` spec through named shared state; a dock references that state key; the browser renderer subscribes and mounts the JSON view; non-reserved action names are forwarded through `rpc.call(action, params)`. Renderer-local reserved actions include `setState`, `pushState`, `removeState`, and `validateForm`. The action bridge is not itself a contribution authorization or provider-selection policy. The new runtime must resolve and authorize actions at its adapter boundary and return per-provider outcomes. [View creation](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/json-render/src/node/create-view.ts), [dock renderer](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/json-render-ui/src/dock-renderer.ts), [action bridge](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/json-render-ui/src/action-bridge.ts).

The reusable renderer boundary is a DOM mount/dispose contract plus JSON data and RPC/state access. Contributions need not author Vue components. The reference implementation's framework is therefore compatible with framework-neutral contributions. Whether the existing context can be satisfied cleanly across every extension surface still requires the rendering experiment; successful bundling alone does not answer that. [JSON-render hub contract](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/json-render/src/hub.ts), [renderer module](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/json-render-ui/src/renderer-module/index.ts).

The exact type gap belongs to #12: `JsonRenderDockRenderer` accepts `DockRendererMountOptions`, whose `context` is the full `DevframeClientContext`. Its `DevframeRpcClient` declares `transport` as `websocket | sse | static`. The reference implementation uses the narrower runtime subset `rpc.call`, `rpc.sharedState.get` and `rpc.connectionMeta.backend`, but a Port-backed object with those fields does not thereby satisfy the full public type. Choose a supported narrower renderer-host interface, a local wrapper or an upstream extension point. Do not use a cast or a fabricated WebSocket transport value as evidence that the existing public contract supports extension Ports. [Mount contract](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/hub/src/client/renderers.ts), [RPC client type](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/devframe/src/client/rpc.ts), [renderer usage](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/json-render-ui/src/dock-renderer.ts).

DevTools kit calls `createHubContext`, which wraps the Devframe host context, and attaches optional `viteConfig`, optional `viteServer`, and `createJsonRenderer`. These are layered raw contexts, not three mutually exclusive provider realms. A provider identity, execution context, surface, and native primitive bundle should remain separate concepts; the exact public discriminant belongs to #5. Never serialize those raw contexts through contribution state. [Kit context](https://github.com/vitejs/devtools/blob/ad2d6df720a513670f93ac09318ae6dc8b4a0623/packages/kit/src/node/context.ts).

A page action follows the in-page channel's call/event path and page/panel endpoint lifecycle, then any host-specific backend operation. An extension adapter still must choose its isolated-world/main-world bridge, validate incoming messages, and connect the backend transport. A server operation instead executes inside the registered Node RPC/service context. These distinct paths must have separate native-context and permission tests. [Page-channel source](https://github.com/devframes/devframe/tree/18fa60effeb928eb445add2a536cd44906a59981/packages/devframe/src/in-page-channel), [Node host functions](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/devframe/src/node/host-functions.ts).

### Live production builds are not static snapshots

The Vite hub adapter mounts a live host with `configureServer`; it disposes the old hub on Vite restarts. Its build integration calls `buildHub` to emit a static snapshot. No `configurePreviewServer` hook appears in the inspected adapter. The live hub reads renderer files on each HTTP request with `Cache-Control: no-store`, but the browser renderer registry caches loaded modules and browsers cache module evaluation by URL. Serving new bytes alone does not replace an already mounted renderer. [Vite hub adapter](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/vite/src/hub.ts), [hub asset serving](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/hub/src/node/initiate.ts), [renderer registry](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/hub/src/client/renderers.ts).

DevTools has a standalone context configured with build/production defaults, showing that compiled production assets and a live backend are compatible concepts. This is a reuse lead, not an observed `vite build --watch` + `vite preview` integration. The final contract must separately cover asset rebuild, host-code restart, renderer invalidation, UI reload, extension worker restart and state restoration. The renderer package's published `watch` script runs `tsdown --watch`; its full build also runs CSS generation and two Vite builds. That script alone does not establish continuous rebuilding of the prebuilt renderer asset. [Standalone source](https://github.com/vitejs/devtools/blob/ad2d6df720a513670f93ac09318ae6dc8b4a0623/packages/core/src/node/standalone.ts), [published renderer scripts](https://registry.npmjs.org/@devframes%2fjson-render-ui/1.0.0).

### Optional CDB composition

The embedded bridge provides an in-process client/broker with a cloning boundary and target executor registration. The selected-tab publisher supplies a Chrome-oriented executor through injected debugger operations. Combining these in an extension is plausible from source and browser bundling, but the provider's registration, approval, claim/release, scope revocation, watch and reconnect methods still need a concrete adapter. “Both accept callbacks” is insufficient evidence that the full composition works. [Embedded bridge](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/core/src/embedded.ts), [provider connection contract](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/extension/src/provider-connection.ts).

For server-backed CDB, the public Devframe connection helper is preferable to opening a second socket merely to reuse the broker. It attaches an existing connection-bound client and disposes logical work when that peer changes. A WebSocket transport remains a separate optional composition. The CDB command catalogue reserves `Fetch.enable` and `Fetch.disable`; therefore arbitrary response interception cannot be promised by tunnelling those commands through the generic client without a specific supported mechanism. This must be resolved with the transform/debugger contracts. [Devframe connection](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/devframe/src/connection.ts), [catalogue](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/core/src/cdp-catalogue.generated.ts).

## Experiments performed

All probes ran in a disposable directory within the isolated research worktree. SDK packages came from `https://registry.npmjs.org/`, with install scripts disabled and automatic peer installation disabled. Tool versions were Node **26.9.0**, pnpm **12.5.1**, and Rolldown **1.2.6**. No Chromium or Firefox process, extension host, Vite live server, or mounted renderer was exercised.

### Browser import-graph check

Each probe entry contained `export * from 'public-package/subpath'`. Rolldown used `platform: 'browser'`, `treeshake: false`, `tsconfig: false`, ESM output, and a guard rejecting Node builtins plus unresolved imports. Generated chunks were inspected for remaining external imports. Disabling ambient tsconfig discovery corrected an initial probe configuration failure; those initial failures were not package failures.

**Passed, with no external imports:** `devframe/client`, `devframe/rpc/client`, `devframe/utils/shared-state`, `devframe/in-page-channel`, `@devframes/hub/client`, `@devframes/json-render`, `@devframes/json-render/hub`, `@devframes/json-render/node`, `@vitejs/devtools-kit/client`, `@dvcol/cdb/embedded`, `@dvcol/cdb-extension`, `@dvcol/cdb-extension/chrome`, `@dvcol/cdb-devframe/client`, `@dvcol/cdb-devframe/connection`, `@dvcol/cdb-birpc/client`, `@dvcol/cdb-websocket/browser`.

**Rejected as expected:** `@devframes/json-render-ui/hub` reaches `node:url`; `devframe/node` reaches `node:process`; `@dvcol/cdb-devframe` reaches `node:buffer`. This validates the need for separate Node/browser imports. The extension package's dependency on `@dvcol/cdb-broker` did not introduce Node builtins into the tested browser entry graph.

Calling `jsonRenderUiRenderer()` in Node and bundling its returned `file` succeeded: one ESM chunk, **701,641 bytes**, no external imports. This is an unminified, tree-shaking-disabled probe size, not a production size budget or proof of extension CSP compatibility.

Reproduction core, using Rolldown and exact SDK versions listed above:

```js
import { builtinModules } from 'node:module';
import { rolldown } from 'rolldown';

const builtinNames = new Set(builtinModules.map((name) => name.replace(/^node:/, '')));
const bundle = await rolldown({
  input: 'entry.mjs',
  platform: 'browser',
  treeshake: false,
  tsconfig: false,
  external(specifier) {
    if (specifier.startsWith('node:') || builtinNames.has(specifier)) {
      throw new Error(`Node builtin in browser import graph: ${specifier}`);
    }
    return false;
  },
  onLog(level, diagnostic) {
    if (level === 'warn' && diagnostic.code === 'UNRESOLVED_IMPORT') {
      throw new Error(diagnostic.message);
    }
  },
});
try {
  const { output } = await bundle.generate({ format: 'esm' });
  const chunks = output.filter((item) => item.type === 'chunk');
  const internalNames = new Set(chunks.map((chunk) => chunk.fileName));
  console.log(chunks.flatMap((chunk) => chunk.imports).filter((name) => !internalNames.has(name)));
} finally {
  await bundle.close();
}
```

### Released-package runtime probe

A Node `MessageChannel` connected two `createRpcClient` instances through actual `postMessage`, message listener registration and removal. `$call('add', 2, 3)` returned `5`. After a second operation reached its handler and remained pending, client `$close(new Error('transport disconnected'))` rejected it with that reason and removed the channel message listener. Closing the server removed its listener too. This verifies explicit close behavior; **it does not prove that a browser Port disconnect automatically calls `$close`**. The wrapper defaults RPC timeout to `-1`, so adapters must not omit disconnect handling.

`createSharedState` with patches mirrored a mutation into another real shared-state instance; reusing the same synchronization ID did not apply a second mutation, and unsubscribe prevented a later callback. An empty embedded CDB bridge returned `[]` from `client.listTargets()`; after `dispose()`, the same client call rejected. All three probes passed. No browser APIs or fake Chrome implementation were involved, and no debugger target or CDP command was tested. [RPC implementation](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/devframe/src/rpc/client.ts), [state implementation](https://github.com/devframes/devframe/blob/18fa60effeb928eb445add2a536cd44906a59981/packages/devframe/src/utils/shared-state.ts), [embedded bridge implementation](https://github.com/dvcol/chrome-debugger-bridge/blob/4053273d6d15ddb17abc3e1b14fc8d58122cb49a/packages/core/src/embedded.ts).

## Required examples and conformance inventory

The monorepo must ship runnable examples for **every piece**: contribution authoring, renderer, standalone Devframe host, Vite DevTools host, Chromium extension host, Firefox extension host, and each optional adapter actually supported. An example must start from documented commands and perform observable work in its real host; no placeholder package, compile-only sample, or browser mock counts as final proof.

For every public SDK export, method, hook, event, option that changes behavior, and feature, record a stable inventory key, runnable example entry point, host/surface matrix, expected result, failure cases, lifecycle cases, and test location. This concerns the new SDK's complete public contract, including any upstream APIs deliberately re-exported. Avoid wholesale upstream re-exports unless their entire supported surface is intended and covered. Internal vendor functionality that is not exposed is not automatically an SDK feature.

Minimum evidence groups:

| Group                       | Required observable paths                                                                                                                                                                                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Contribution lifecycle      | Register, activate, disable, replace/reload, dispose; duplicate identity and invalid declaration; cleanup after activation failure. UI-only, action-only, state-only, transform-only, native-only and mixed contributions.                                    |
| Capabilities/native context | Every supported capability and explicit unavailable result; local raw context narrowing; browser-only and Node-only facilities cannot leak across serialization.                                                                                              |
| RPC/actions/routing         | Per-provider success/failure; default and overridden selection; broadcast/selector/identifier-or-realm precedence; timeout, cancellation, unavailable provider, disconnect and reconnect without duplicate execution.                                         |
| State/views                 | Full and patch updates, synchronization IDs, subscribe/unsubscribe, discovery, invalid schema, missing/removed state, separate provider state, persistence scopes, stale generation and restart recovery.                                                     |
| Renderer/surfaces           | Same contribution/spec on Devframe and DevTools, plus actual popup, options, devtools panel, supported browser panel/sidebar and content UI. Controls, action errors, missing renderer, focus/accessibility, resize, unmount/remount and listener cleanup.    |
| Injection/transforms        | Head/index script insertion, target/frame identity, supported request/response/HTML phases, order, permission denial, navigation, teardown and explicit unsupported operations.                                                                               |
| CDB if accepted             | Actual command/event round trip, provider/target discovery, approval, claims/releases, permission denial, detach, generation replacement, cancellation, subscription cleanup and worker recovery. Each supported transport and browser gets its own evidence. |
| Reload/preview              | Dev HMR and watched production build/live preview; separate UI, renderer, content, worker and server changes; recovery expectations and failures for each layer.                                                                                              |

Every supported API/host cell must execute successfully; explicitly unsupported cells must assert the documented unavailable result. Failure and lifecycle tests add to successful paths rather than replacing them. Use package/unit tests for pure logic and **real browser/server hosts for their final integration claims**. Coverage cannot be reduced to one portable button or a passing import graph. [Examples and API coverage contract #14](https://github.com/dvcol/devkit-extension/issues/14) must settle discovery/enforcement, and [Portable contribution proof #15](https://github.com/dvcol/devkit-extension/issues/15) must exercise the resulting complete declared surface.
